# Vuln Hunting（主动漏洞挖掘方法论）

在**已授权**前提下，从目标的**实际行为**里找出**没有公开 CVE 的漏洞**。

本 skill 不是「漏洞清单」，是**一套换维度的思维模型**：同一功能换个角度问，答案就可能不同。

---

## 边界与禁止（Agent 必读 · 违反即越界）

| 允许 | 禁止 |
|---|---|
| 在授权范围内做**低影响的验证**（读自己的数据、改自己的测试数据） | 破坏性操作（删数据、格式化、改他人数据） |
| 用**两个身份**做对照（自己的低权账号 vs 自己的高权账号） | 提权到不属于你的账号、改他人口令 |
| 并发/竞态验证用**小规模**（2~5 并发） | 大规模压测、拒绝服务、flood |
| 读取自己有权访问的数据来证明越权 | 批量拖库、大范围读取无关数据 |

**判定标准**：你的验证应该是「**证明存在**」，不是「**造成破坏**」。

---

## 核心原则：换维度，而不是换 payload

同一个接口、同一个功能，**换个维度看**会得到不同的问题。挖掘时不要只想着「换 payload 再打一遍」——那是在同一个维度里打转。

**七个维度**（每个下面都有具体手法）：

### 维度 1：对象换位 —— 换个身份/角色调用会怎样？

**核心问题**：这个操作在「你是你」时成功；如果**你是另一个人**，会怎样？

具体手法：
- **水平越权**：把请求里的对象 ID 换成**你自己账号下的另一个对象**（`user_id=1002` → `1003`）。成功 = 越权。
- **垂直越权**：把请求里的角色/权限字段改成**更高权限**（`role=user` → `role=admin`）。成功 = 提权。
- **未授权调用**：**完全去掉**认证头/cookie，直接调接口。成功 = 认证缺失。
- **对象类型混淆**：URL 里的 ID 类型换了（`/order/123` → `/order/abc`、负数、超大数、`0`）。

**验证要点**：两个账号都要是**你自己的**（低权 + 高权），用差异证明。

**差异怎么算**：用 `diff_responses` 工具——它对比两个响应的**结构性差异**（状态码、JSON 键集合、值差异），并自动滤掉时间戳/trace id/随机串这类噪声。**多出来的键往往就是越权拿到的数据**。
用法：把两个响应各自用 `curl -i` 存成文件（存到本意图工作目录），再给 `diff_responses` 传 `file_a`/`file_b`。
**差异本身不是漏洞**——工具给的是「哪里不同」，是不是漏洞要你结合语义判断（比如 `role` 字段不同是提权，`email` 不同只是数据不同）。

### 维度 2：流程拆解 —— 跳过某一步会怎样？

**核心问题**：正常业务流程有 A→B→C 三步；**只做 C** 会怎样？

具体手法：
- **跳过校验**：注册流程要验证邮箱，直接调「设置密码」那一步
- **跳过支付**：下单要支付，直接调「发货」接口
- **跳过审核**：内容要审核，直接调「发布」接口
- **直接调后续接口**：从抓到的前端流量里挑一个「最后一步」直接调
- **重放**：把成功请求原样重发（看是否幂等——可能重复扣款/重复发货）

**验证要点**：找到「前端调用了但后端没校验前置状态」的那一步。

### 维度 3：状态机 —— 同一接口在不同状态下行为不同吗？

**核心问题**：订单/工单/审批有生命周期；**在不该允许的状态下**调用会怎样？

具体手法：
- **非法状态转移**：未支付就确认收货、未审核就发布、已取消的订单再取消
- **状态回退**：已完成的流程再走一遍（回退审批、撤销退款）
- **竞态**：**并发**提交同一操作（2~5 并发），看是否出现重复处理
  - 典型：并发下单超卖、并发优惠券核销、并发转账
  - 手法：同一请求**同时**发 N 份（用 `for i in $(seq 5); do curl ... & done; wait`）
  - 关键：**先看有没有唯一性约束**——有唯一索引的竞态多数不可利用，别浪费时间

**差异怎么算**：同一接口在「合法状态」和「非法状态」下各取一次响应，用 `diff_responses` 工具对比——**状态码或响应体结构不同**，说明服务端对非法状态走了不同的分支（可能没校验、可能只在前端挡了）。

### 维度 4：数据边界 —— 数据从哪来、经过谁、到哪去？

**核心问题**：**哪些输入是攻击者可控的**，而系统却当成了可信数据？

具体手法：
- **信任边界**：前端 JS 里的字段（`isAdmin`、`price`、`userId`）后端信了吗？
- **隐藏参数**：改一个没在界面上出现的参数（`role`、`is_vip`、`status`）看后端认不认
- **注入点**：所有进入 SQL/命令/模板/LDAP/表达式的地方
  - 找点：`grep` 源码（若有）、或看报错、看参数回显
- **二阶注入**：先存进去（评论/昵称/备注），再让它在别处被解析

**验证要点**：**证明可控**比「找到一个可疑参数」重要——要看到它影响了结果。

### 维度 5：资源假设 —— 服务假设了什么？

**核心问题**：如果这个假设不成立会怎样？

| 假设 | 破坏方式 | 后果 |
|---|---|---|
| **唯一性** | 同一时间两次提交 | 超卖、重复发放、重复核销 |
| **顺序** | 跳过中间步骤直接到末步 | 绕过审核、绕过支付 |
| **并发** | 同时操作同一资源 | 竞态覆盖（TOCTOU） |
| **限额** | 超限/绕过计数 | 绕过频率限制、白嫖 |
| **大小/长度** | 超长/超大输入 | 截断绕过、DoS、资源耗尽 |
| **存在性** | 引用一个不存在的对象 | 空指针、默认放行 |

**验证要点**：找到「系统假设了某事，但没校验」的地方。

### 维度 6：错误路径 —— 出错时系统怎么处理？

**核心问题**：正常路径都测过了；**出错时**会怎样？

具体手法：
- **报错泄露**：把参数改成非法值，看报错里有没有路径/表名/密钥/内网地址/SQL 片段
- **异常吞掉**：某步失败了，流程还继续吗？（后面几步是不是用了默认值）
- **默认值不安全**：失败时默认放行、默认 admin、默认跳过校验
- **错误码差异**：同一接口对「不存在」和「无权限」返回不同 → **可枚举**
  - 手法：把 ID 从 1 递增扫，对比状态码/响应长度/响应体差异
  - **用 `diff_responses` 对比「存在」与「不存在」两个响应**：状态码不同或 JSON 键集合不同 → 存在可枚举
  - **前提**：两个响应要**同身份、同参数形状**（只换一个 ID 值），否则差异是噪声不是信号

### 维度 7：组合 —— 两个单独无害的操作合起来呢？

**核心问题**：每个单看都正常，**组合起来**就不正常了。

具体手法：
- **权限提升链**：低权能改资料 → 资料里有能提权的字段 → 改了就提权
- **存储型 XSS**：写进去（评论/上传）→ 别人看时触发 → 拿高权 cookie
- **缓存投毒**：改了内容但缓存没清 → 别人看到的是你的
- **上传 + 解析**：上传一个文件 → 后端解析它 → 解析器有洞（XXE、路径穿越、SSRF）
- **重放 + 换参**：先正常调一次拿到 token/ticket，再把 token 用在别的对象上

## 挖掘流程（照着走，别跳步）

```
第 0 步  选定目标功能   —— 一个具体的接口/页面/流程（不是「整个站」）
第 1 步  建立基线        —— 正常用一遍，抓完整流量（traffic_search / 浏览器抓包）
第 2 步  画出这个功能的  —— 角色有哪些？状态有哪些？步骤有哪些？参数有哪些？
         「状态与角色图」   ★ 这一步不能跳，跳了就是盲打
第 3 步  逐维度过一遍    —— 按上面 7 个维度，每个维度问自己那个核心问题
第 4 步  找到「差异点」   —— 成功/失败两种结果的差异（响应码/长度/内容/副作用）
第 5 步  最小化验证      —— 只用最少的步骤复现，确认不是偶然
第 6 步  换路径复现      —— 用不同参数顺序/不同客户端/不同身份再打一次
                            （★ 对抗式自检：证伪和证实同等有价值）
第 7 步  写回            —— 真触发过 + 有可复现证据 + 通过第 6 步 → report_finding
                            否则 → record_fact（记一条 inferred：嫌疑点 + 为何未确认）
```

## 与「已知漏洞」的区别

| | 查 CVE | 挖 0day |
|---|---|---|
| 依据 | 公开漏洞库 | **目标自身的行为** |
| 起点 | 「这个组件有什么漏洞」 | 「这个功能有什么反常」 |
| 工具 | `search_vulns` / `search_recent_critical` | 流量回看 + 参数对照 + 并发脚本 |
| 产出 | 「可能受影响」→ 需实际触发 | 直接是「已触发的真实缺陷」 |

**两者是互补的，不是替代**：先用 CVE 情报打「已知面」（快），再用本方法论打「未知面」（慢但可能拿到高价值）。

## 常见失败模式（自查）

| 失败模式 | 表现 | 纠正 |
|---|---|---|
| **盲打** | 不看流量直接猜参数 | 第 1 步必须先抓基线流量 |
| **只在一个维度打转** | 反复换 SQL payload 换编码 | 停下来，走完 7 个维度 |
| **把「版本命中」当漏洞** | 查到 CVE 就报 finding | 必须**实际触发**才有 finding |
| **不可复现就报** | 手工点一次成功就记 finding | 必须换路径复现一次 |
| **越界** | 删数据、压测、提权到他人账号 | 只用**自己的两个账号**做对照 |
| **大范围读取** | 一个脚本导出全库 | 证明越权只需读**一个**越权对象 |

## 配套工具（本机）

| 目的 | 工具 |
|---|---|
| 看真实请求/响应 | `traffic_search` / `traffic_get` / `traffic_blob`（先查流量，别重复 curl） |
| 拿到接口清单 | `api_contract` 工具（读目标的 OpenAPI/Swagger 契约——比爬虫准）；没有契约用 katana / `api-recon` skill |
| 改包重放 | `curl` / `python3` 脚本（写到本意图工作目录） |
| 并发竞态验证 | `python3` 脚本（2~5 并发，小规模） |
| 参数差异对照 | `diff_responses` 工具（对两个响应做结构化差分，自动滤时间戳/trace id 等噪声） |
| 目录/参数枚举 | `ffuf` / `feroxbuster` / `gobuster` |
| 接口枚举 | `katana` / `api-recon` skill |
| Web 指纹 | `whatweb` / `httpx` / `wafw00f` |
| 主机/服务侧 | `nmap` / `naabu` |

**中间件协议专项**（MQTT/AMQP/Mongo/MySQL/PostgreSQL/Redis/SOAP/GitLab/网络设备）见「宿主环境」页的「中间件协议」组——装好后可直接用对应库跟目标说话。
