# 模型路由策略（v0.3.95 B11）

> 配置面早已就绪：goals / planner / worker / mainagent / judge / compactor 六个角色
> 各有独立 LLM 解析（Agent 绑定 → 任务链 → 全局激活；judge 还有独立 profile+prompt+超时）。
> 本文档落的是**策略与默认建议**——哪个角色该配什么档位的模型、为什么。

## 一、角色 × 模型档位建议

| 角色 | 建议档位 | 理由 |
|---|---|---|
| **planner** | **强推理（thinking）** | 判断型任务：去重、接续归因（stop_reason）、目标判定（prove_goal 量化核对）、深度-广度仲裁。每轮短、system 静态利于缓存——强模型的判断力花在刀刃上 |
| **worker** | **强执行 + 中推理** | 每轮全量工具循环，thinking 会拉长每步延迟并挤占 idle-stop 计数窗口（thinking-only 回合既不写回也不被 nudge 救——nudge 只挂在 Stop）。若用 thinking 模型，run_timeout 必须留裕量 |
| **judge（拦截裁决）** | **非思考 / 低思考** | 180s 超时是硬约束：思考型模型耗时要 32768→65536 升预算重试；裁决质量来自 prompt 结构（双轴判据+对照样例）而非模型深度 |
| **goals（目标拆解）** | **便宜模型** | MaxTurns=8 的结构化抽取任务（set_goals/set_constraints），旗舰模型无收益 |
| **compactor（上下文压缩）** | **便宜、非思考** | 纯摘要任务。此前绑 planner 同模型烧 65536 token + 20 分钟墙钟——压缩调参的全部痛点源于此。v0.3.95 起支持独立配置，默认应降档 |
| **mainagent（人在环路）** | **强推理** | 与 planner 同级判断（steer/kill 前的取证、补意图），交互频次低，质量优先 |

## 二、三通道池的分工建议

三通道轮询（llm_pool）解决**可用性**；角色路由解决**质量与成本**。两者正交：

- 免费通道（`:free` 档 / flash 档）：适合 worker / goals / compactor——量大、单步浅。
- 付费/旗舰通道：优先给 planner 与 mainagent——每轮短、判断密度高，token 花得值。
- judge 建议固定绑一个稳定通道（`llm_judge_profile_id`），裁决路径不要参与池子轮询——
  裁决中途熔断会走 fail_action（默认 ask），扰动审批体验。

## 三、thinking 预算

`MaxTokens` 是思考+正文共用预算。思考型模型配小了会把「模型在思考」误判成
「正文为空」触发升预算重试。v0.3.95 前**没有**独立 thinking 旋钮——配 thinking
模型时 MaxTokens 给足（≥32768），并把超时同步放大。

## 四、不做的事

- **按错误率动态升降模型**：状态复杂、可解释性差；现有「绑定 + 任务链 + 手动切换
  + 审计事件」已覆盖。
- **judge 用 thinking**：见上，超时风险大于收益。
