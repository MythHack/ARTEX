# 漏洞挖掘能力：与开源同类产品对比

> 2026-10-22 盘点。目的：把「挖掘漏洞」这条能力线（方法论 → 情报 → 工具 →
> 证据 → 编排 → 闭环）与开源同类产品对照，找出**还缺什么**。
>
> 本文的每条结论都标了**证据来源**——「代码里确凿没有」的比 grep 静默无输出
> 更可靠（本次盘点中曾两次因 grep 无输出而误判能力缺失，实际都存在）。

## 二、确认的缺口（代码里确凿没有）

| # | 缺口 | 影响 | 证据 |
|---|---|---|---|
| **G1** | **无 fuzzing 引擎** | vuln-hunting 里「数据边界」「资源假设」两个维度本质要靠 fuzz 找边界。现在只能让模型手写脚本——覆盖率与效率都不可控 | hosttools 里 boofuzz/radamsa/atheris/hypothesis/schemathesis 全为 0 |
| **G2** | **无差分/基线对比工具** | 方法论里「对比两个响应找差异」是核心手法（越权、枚举、状态机三类都靠它），现在只能靠模型手写 python 做 diff | hosttools 里 diff 类工具 0 |
| **G3** | **无代码资产 / 源码仓库概念** | semgrep 装了但只是二进制，**扫完的结果进不了图谱**，worker 也拿不到源码上下文。SAST 与动态挖掘之间**没有桥** | `db/assets.go` 里 source_repo/code_asset 类概念 0 |
| **G4** | **无利用链编排** | 有 `steer_work`（人工纠偏），但没有「A 成功后自动派 B 去用成果」的链式机制。串行链完全靠 planner 自己在图上判断 | `agent/planner.go` 的接续纪律是**文本约定**（填 `continues` 字段），不是机制 |
| **G5** | **无鉴权态/多身份管理** | 水平越权的前提是「两个身份」。资产里有 `auth` 字段，但**没有「用这个账号去调这个接口」的工具**——模型得自己拼 curl | hosttools/agent 工具里无凭据复用类工具 |

### 4.0 全行业共识与 ARTEX 的位置

**共识（几乎所有项目都有）**：

1. **多 agent 编排**：编排者不碰目标、专职子 agent 执行
2. **「必须有 PoC 才报」**——无利用不报，是行业门槛
3. **容器/沙箱隔离**执行目标
4. **CI 集成 + SARIF/Markdown 多格式报告**
5. **HTTP 拦截代理 + 浏览器自动化**双验证通道
6. **范围与权限约束**（越界是最大风险）
7. **多 LLM provider 可插拔**

**★ ARTEX 在这里的判断**：

- 共识项 1/2/3/4/6 我们**都有**（编排/对抗式自检+证据/hostd 隔离+报告+triage/管控规则）
- **「按时间流的持续情报运营」全行业几乎没人做**——只有 CAI 明确用 NVD/MITRE/GHSA 拉最新公告；
  Strix 是「资产匹配已知 CVE」；其余基本是静态知识库。
  **没有一个做成「最近 7 天爆了什么 → 匹配我的资产 → 排队列」。**
  **这正是 ARTEX 快通道做的事——这是我们的领先项，不是短板。**

**★ 一个我们不占优、但被低估的短板**（调研原话）：

> 「CVE 情报匹配普遍不做可达性/受影响版本判定，容易把不可达依赖报成高危。」

**我们撞上了同一堵墙**：PHP 那两个 CVE 的 NVD 版本区间是**空的**（`cpe:2.3:a:php:php:*:*`）。
我们目前只能标「版本待定」——**这只是止损，不是解法**。解法是**再接一个版本区间来源**
（GitHub Advisory Database 的 GHSA API / OSV.dev），见 M10。

### 4.1 关键机制差异（ARTEX 已有 / 缺 / 可借鉴）

| 机制 | pentagi | Anthropic-Skills | ARTEX 现状 |
|---|---|---|---|
| **执行监控 + Mentor 干预** | 有：Adviser agent 在执行模式异常时自动介入；**Progress Analysis 专门检测循环与低效** | — | 有 `idlestop`，但**固定规则**（连续 3 轮零写回），非 LLM 判断 |
| **任务预拆解** | 有：Planner 先拆 3-7 个具体步骤再派专员 agent；**Scope Management 防范围蔓延** | — | planner 一次派 ≤4 条意图，**无显式预拆解步骤** |
| **skill 的标准化标签** | — | 有：每个 skill 映射 ATT&CK/CSF/ATLAS/D3FEND/AI RMF/F3 中**相关的那些**，用官方库校验 | **完全没有标签**——skill 不能按 ATT&CK/CWE 检索、不能统计覆盖度 |
| **skill 规模与领域** | — | 818 skill / 34 领域 | **4 个 skill**（api-recon / playwright-cli / scopesentry / vuln-hunting） |
| **向量记忆** | 有：pgvector 记住「什么有效」 | — | 无向量检索；只有图谱（事实/资产/发现/hint） |
| **知识图谱** | 有：Neo4j 追踪 host/service/finding | — | 有（PostgreSQL 图谱），**但无向量记忆** |
| **工具隔离执行** | 有：Docker 沙箱 | — | 有（hostd 特权助手 + 管控规则） |
| **行为可观测** | 有：langfuse + grafana | — | 有 journalctl + 拦截历史，**无 agent 行为追踪** |
| **情报源** | — | — | **NVD + CISA KEV + PoC + nuclei + 资产联动 + 近期高危快通道**（这层我们不弱） |
| **协议工具广度** | 20+ | — | **54 个（含 15 个中间件协议库）**（我们更广） |
| **漏洞验证** | 报告 + 利用指南 | — | 有：对抗式自检（换身份/换参数/换客户端复现）+ traffic 证据绑定 + 8 种 triage |
| **裁决层** | 无（结论即模型输出） | 无（相关性分析） | **裁决是模型自述**——这是短板（M20） |
| **模型隔离** | 自认短板：Challenger 与生成同模型，有共享盲区 | 不适用 | **judge 与 worker 走不同模型/上下文**——结构上能做「不同模型对抗复检」，但**目前没用起来** |

### 4.2 从对比中看出的、ARTEX 值得补的机制（按性价比排序）

| # | 机制 | 来源 | 为什么值得 | 成本 |
|---|---|---|---|---|
| **M1** | **skill 的标准化标签**（CWE / ATT&CK / 漏洞类型） | Anthropic-Skills | 现在 skill 是「孤岛」：不能按 CWE 检索、不能统计「这类漏洞我们有没有方法论」、不能做能力矩阵。加上标签后，**任务来了可以按标签选 skill**，而不是靠模型记忆 | 低——frontmatter 加字段 + 一个检索接口 |
| **M2** | **差分/基线对比工具** | 通用（ARTEX 自缺） | vuln-hunting 三个维度（越权/枚举/状态机）核心手法都是「对比两个响应」，现在只能让模型手写 python | 低——一个脚本 + 一个工具 |
| **M3** | **凭据复用工具** | 通用（ARTEX 自缺） | 资产里**已经有** `auth` 数据，但只能当文本读；越权挖掘的前提是「两个身份」 | 低——一个工具（读资产 auth → 带认证发请求） |
| **M4** | **LLM 版的循环/低效检测** | pentagi（Progress Analysis） | 现在的 `idlestop` 是「连续 3 轮零写回」的固定规则，**测不出「有写回但在原地打转」**（换措辞重复同一件事）。这类空转是真实成本 | 中——需要分析执行轨迹的 LLM 调用 |
| **M5** | **规划器的显式预拆解** | pentagi | 现在 planner 一次派 ≤4 条意图，但**没有「先拆成 3-7 个具体步骤」这一层**；复杂目标下容易派得散 | 中——改 planner 提示词 + 可能要新的结构 |
| **M6** | **向量记忆（什么有效/什么无效）** | pentagi（pgvector） | 现在跨意图的经验传递靠 fact 文本；「这条路走不通」这类负面经验很容易丢 | 高——要引入向量库 + 检索 |
| **M7** | **fuzzing 引擎接入** | 通用（ARTEX 自缺） | 「数据边界」「资源假设」两个维度本质要 fuzz | 中——装 boofuzz/schemathesis/atheris + 编排 |
| **M8** | **代码资产/SAST 联动** | 通用（ARTEX 自缺） | semgrep 装了但结果进不了图谱，源码上下文 worker 也拿不到——**动态挖掘与静态审计之间没有桥** | 高——要引入「代码资产」这个新概念 |
| **M9** | **利用链的机制化编排** | 通用（ARTEX 自缺） | 现在串行链靠 planner 在图上判断 + `continues` 文本字段约定，没有「A 成功后自动派 B」的机制 | 高 |
| **M10** | **版本区间的第二数据源**（GHSA / OSV） | 调研共性短板 | NVD 对新披露的 CVE **经常不填版本区间**（PHP 那两个 CVE 就是 `cpe:2.3:a:php:php:*:*`）。我们只能标「版本待定」——止损但不是解法。接 GHSA/OSV 可拿到受影响范围 | 中——又一个数据源，结构类似 NVD |
| **M11** | **三态收口**（confirmed / ruled_out / open_proof_gap） | Strix（counterevidence） | 我们现在是「确认了才报 / 没确认就不报」两态。Strix 强制 `ruled_out` **必须指名控制点**（哪个防护、位于攻击路径何处、为何先于 sink 执行），`open_proof_gap` 显式留账。**我们「探到边界」这个判断目前是模型自述，没有证据要求** | 中——改 report/record_fact 的字段语义 |
| **M12** | **覆盖台账**（每面都有结论） | Strix（SARIF coverage）/ Shannon（WSTG 勾选表）/ AutoPentest（覆盖率报表） | 「查过且干净」≠「没看过」。我们有 coverage 概念，但**不产出「哪些面查完了」的台账** | 中 |
| **M13** | **PoC 沙箱验证层** | Strix（Exploit Runtime） | 我们止于「检索 PoC」+ 对抗式自检（换路径复现）。Strix 是「PoC 在沙箱里对目标**真跑通**才标 verified」——把「情报命中」与「漏洞成立」彻底分开 | 高——要执行环境 |
| **M14** | **API 契约驱动枚举** | Strix（直读 OpenAPI/Swagger/Postman） | 我们靠爬虫（katana）与 fuzzing 发现接口。**契约文件是更准的接口清单来源**——它直接回答「有哪些接口、哪些参数、哪些方法」 | 低——读契约文件 + 解析 |
| **M15** | **结构化攻击面图 + 角色权限格** | Shannon（trust zone / 角色支配关系） | 越权挖掘的前提是「有哪些角色、谁能访问什么」。我们没有**结构化的权限模型**——只能靠模型从流量里现推 | 高——要新数据模型 |
| **M16** | **决策/生成/解析三模型分离** | PentestGPT | **直接对冲 ARTEX 已知的思考型模型预算陷阱**（记忆里那条：minimax-m3.1 强制 thinking 吃光输出额度，导致压缩/裁决空回复）。只把决策点交给强模型，生成/解析走便宜模型 | 中——要改 provider 层 |
| **M17** | **WAF 绕过自适应 + 场景化 payload** | AutoPentest（按 sink 上下文给 payload） | 我们现在给的是通用 payload 字典。按 sink 类型（sql_string/command_shell/html_body）给不同形态，成功率会高很多 | 中 |
| **M18** | **未授权 prompt 注入防护**（输入+输出双向） | CAI（guardrails，Base64/32 感知）/ Nebula | 我们把目标内容喂进模型（抓到的页面、报错、响应体）——**这是必然的注入面**。目前靠模型自身的判断 | 中——需要输出侧的解码/同形字检测 |
| **M19** | **成本与单位发现成本可见** | Nebula（token/cache）/ PentestGPT（pricing）/ AutoPentest（实测 $96/次） | 我们有 llm_usage 统计，但**没有「单位发现成本」**——不知道哪个意图/工具组合性价比低 | 低——已有数据，缺聚合视图 |
| **M20** | **确定性裁决层与 LLM 判断层强制分离** | OpenAnt | OpenAnt 的硬规矩：模型只输出「带逐字引用的具体事实」，**由代码核对引文是否真出现在模型看过的证据里**再推导裁决——「模型的自我判定永远不作数」。我们现在是**模型直接输出结论 + triage 状态**，等于让模型自己给自己背书 | 中——改 report/record_fact 的字段语义（要事实+引文，不只是结论） |
| **M21** | **未执行的检查必须报 unverified，禁止静默通过** | OpenAnt | 没跑成的验证报「未验证」而不是「通过」。我们这条线现在就踩着：探到边界但没复现的 finding，状态是模糊的 | 中——三态收口（M11）的具体实现 |
| **M22** | **阶段级模型路由** | OpenAnt | 七个阶段各自配 provider/model：检测/验证/可达性用强模型，上下文构建与报告用轻模型。**直接对冲记忆里那条坑**（minimax-m3.1 强制 thinking 吃光输出额度，导致压缩/裁决空回复）——强模型只用在真需要推理的判断点上 | 中——要改 provider 层（比 M16 三模型分离更细） |
| **M23** | **按 git diff hunk 增量扫描 + pre-commit 钩子** | OpenAnt | 只扫「函数体与 diff hunk 重叠」的单元，成本降一个数量级。可作为**提交前/合并前的第二道关**，不必每次全量复扫 | 中——需要代码资产概念（G3/M8 先做） |
| **M24** | **攻击链/相关性升级** | hexstrike（VulnerabilityCorrelator） | 把多个低危发现按可达性串成链再评估价值。同时解决两件事：压低误报噪声（噪声串不成链）、避免「找到一个就停」 | 高——依赖 G3/利用链编排 |
| **M25** | **MCP 作为 AI Agent 与攻击工具的桥** | hexstrike | hexstrike 150+ 工具全部走 MCP，复用 Claude/Codex 已有的 agent 循环，不自建 LLM 循环。**ARTEX 的 hostd 特权助手 + 工具表本质就是同一思路**，但没有 MCP 出口——外部 agent 接不进来 | 中——hostd 已有特权边界，加 MCP 适配是增量 |

### 4.2.1 两次调研的方法论差异（值得单独记）

OpenAnt 与 hexstrike 走的是**两条相反的路**，这个对比比单个机制更有价值：

| | OpenAnt（源码级） | hexstrike（工具级） | ARTEX（现位置） |
|---|---|---|---|
| **发现方式** | 纯 LLM 推理 + 对抗验证，不依赖 CVE 库 | 工具驱动，LLM 只做调度与选参 | 情报驱动 + LLM 推理（两条都有雏形） |
| **误报控制** | 确定性代码核验引文，**模型自评不作数** | 相关性串链，README 自述误报 2.1%（无第三方复现） | 对抗式自检（换身份/换参/换客户端复现） |
| **产出契约** | CI 退出码契约（0 干净 / 1 发现漏洞 / 2 扫描失败） | 漏洞卡片 + 实时 dashboard | finding + triage 八态 + 证据链 |
| **部署边界** | 只改临时副本，永不自动改目标仓库，部署决定权留给人 | 要求隔离环境，警告 agent 拥有系统级权限 | hostd 特权助手 + 内置管控规则（三层） |

**★ 对 ARTEX 最关键的一条**：OpenAnt 明写「Challenger 与生成用**同一个模型**，所以只是窄化、
没有消除共享盲区」——这恰好指向 ARTEX 的一个**结构性优势**：我们的拦截研判（judge）与
挖掘（worker）走**不同的模型/上下文**。**对抗性复检时用不同模型**，是我们天然能做而
OpenAnt 做不到的事——但目前我们**没把这个优势用起来**（worker 的自检仍在同一上下文里）。

**★ 另一条硬约束**（值得直接抄）：OpenAnt 的「Everything that decides whether a
patch is applicable ... is deterministic code operating on that output」——
裁决必须是确定性代码。ARTEX 的 `record_fact` / `report_finding` 目前接受模型自述的
结论，这就是 M20 要治的病。

### 4.3 ARTEX 明显更强的地方（不要丢）

- **情报层**：资产指纹 → CVE 的自动联动 + 近期高危快通道 + 版本待定标记。多数同类产品的情报是「按组件查」，我们还做了「按时间流」。
- **证据链**：MITM 流量留存 + 四类用途绑定 + 版本化。多数项目只有「报告文本」。
- **管控层**：规则分三层 + 规则级 timeout 真生效。多数项目是「要不要审批」一个开关。
- **协议广度**：54 工具 vs 20+。

## 五、优先级建议（对比后定稿）

**第一批（低成本、高确定性，本轮已在做）**

1. **G5 凭据复用工具**（`auth_request`）—— 越权挖掘的前置条件，且资产里**已经有数据**了（纯浪费）。
   **本轮已实现**（`agent/tools_auth.go`）：按凭据形态选认证方式（token→Bearer / cookie 类型→Cookie 头 /
   账号密码→-u），POSIX 单引号转义（用真 shell 解析验证过），**只组命令不发请求**（走统一的流量录制与审批管控）。
2. **G2 差分对比工具** —— 成本最低（一个脚本），直接服务三个维度的核心手法
   **本轮已实现**（`agent/tools_diff.go` + `agent/tools_diff_test.go`）：
   - **文件模式**：模型用 `curl -i` 存下两个响应 → 工具**读文件直接算**（零网络、零脚本）；
   - **URL 模式**：工具在**本次 run 的工作目录**写出 Python 差分脚本 → 返回一条
     「取两段响应 + 做差分」的命令交 Bash 执行（**请求走记录代理与审批管控**，与
     `scan_with_nuclei`/`auth_request` 同一模式）；
   - 判据：滤掉**值形态**像噪声的字段（时间戳/UUID/trace id/base64），**保留键的增删**
     （多出来的字段往往就是越权拿到的数据）；**凭据类字段的值自动抹掉**；
   - 两份实现（Go 侧与 Python 侧）**必须等价**——有真跑 python 的对照测试逐字段比；
   - 已接进 `vuln-hunting` skill 的三个维度（对象换位/状态机/存在性枚举），
     并替换掉 skill 里"手写 python 做 diff"的旧指引。
3. **M14 API 契约驱动枚举** —— 读 OpenAPI/Swagger/Postman 得到接口清单，比爬虫准
4. **M1 skill 标准化标签**（CWE/ATT&CK）—— 让 skill 可被检索、可统计覆盖度
   **本轮已实现**（`server/skill_tags.go` + 四个内置 skill 已打标）：
   - 标签格式在 SKILL.md frontmatter 的 `tags:` 块（cwe / attack / class 三类）；
     norma 的 yaml 解析忽略未知字段——加了标签的 skill 对 norma 完全透明
     （有守门测试 `TestTaggedSkillsStillLoadWithNorma` 守着这一点）；
   - ARTEX 侧解析器（`LoadSkillTags`），键是**目录名**（与 agent_skill_visibility
     的绑定键一致）；解析失败=没有标签，不是错误（第三方 skill 常无标签）；
   - `GET /api/skills` 返回 tags 字段，skill 管理页显示标签徽章
     （CWE/ATT&CK 用 outline、class 用 secondary）；
   - vuln-hunting 已标 10 个 CWE（覆盖越权/鉴权/IDOR/竞态/组合利用的核心编号）+
     T1190 + 8 个 class；api-recon 标 CWE-200 + T1595.002 + recon 类；
   - **下一步闭环需要**：CVE 条目带 CWE 编号入库（GHSA 的 cwes 字段已在
     `vulnintel/ghsa.go` 解析但未落库）——落库后「查到 CVE → 自动提示对应
     方法论 skill」的检索环就通了。这是第二批的活（要动 schema）。

**第二批（要动数据模型或编排）**

5. **M10 版本区间第二数据源**（GHSA/OSV）—— 直接解决「新 CVE 版本区间为空」这个**全行业共性短板**
   **本轮已实现 GitHub Advisory Database 作为第二来源**（`vulnintel/ghsa.go` / `ghsa_range.go` / `ghsa_store.go`）：
   - **不建新表**——复用 `vuln_cves`（`source='ghsa'`）+ `vuln_cpe_products`，
     `search_vulns` 的检索与版本判定**自动生效**（不写第二套查询，避免两套逻辑不一致）；
   - GHSA 的版本区间是**必填**的（`vulnerable_version_range` + `first_patched_version`），
     semver 区间转成现有的 start/end 列后，`VersionInRange` 三态判定直接可用；
   - **判定保守**：版本解析不出（`8.3.1-dev-build` 这类开发版）、区间算子不认识、
     区间为空——一律判「可能受影响」。判错方向不对称：误判「不受影响」会让模型直接跳过漏洞；
   - **覆盖边界（重要，不夸大）**：GHSA 覆盖**有包生态的组件**（composer/npm/pip/maven/…），
     **PHP 核心自身的 CVE 不在 GHSA 里**（实测 CVE-2026-109618/109619 在 GHSA API 返回空数组）。
     所以 GHSA 是**补充不是替代**——补的是占我们资产大头的「有包生态组件」，
     核心语言的 CVE 仍要靠 NVD + 厂商 advisory；
   - 已在测试机（192.168.198.130）做过端到端验证：真实拉 GHSA → 真实入库 →
     版本判定正确（3.9.0 受影响 / 3.10.0 不受影响 / 3.10.1 不受影响）→
     `search_vulns` 的 product 检索路径命中 → 验证数据已清理。
6. **M11 三态收口**（ruled_out 要指名控制点）—— 治「探到边界」只是模型自述
7. **G1 fuzzing 接入** —— 收益大，但要接进 worker 工作流（不只是装个二进制）
8. **M4 LLM 版循环检测** —— 现在的 idlestop 测不出「有写回但在原地打转」
9. **M12 覆盖台账** —— 「查过且干净」≠「没看过」
10. **M16 三模型分离** —— 直接对冲已知的思考型模型预算陷阱
