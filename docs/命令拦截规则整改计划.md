# 命令拦截规则审查与整改

> 2026-10-21 首版审查，2026-10-22 按**代码真实状态**重做。
> 目标：把「明令禁止」和「交给 Agent 研判」在**规则层**真正分开，
> 并修掉「规则上的 timeout 字段是死字段」这个误导性 bug。
> **不动核心拦截架构**（仍是规则 → judge → allow/ask/deny 三分支）。

---

## 一、审查结论（含一处重要的自我更正）

### 首版结论的前提是错的

首版审查（2026-10-21）写的是「21 条内置规则，20 条 judge + 1 条 deny」。**实际不是**：

| | 首版文档写的 | 代码真实状态 |
|---|---|---|
| 内置规则数 | 21 | 22（含 v3 删除接口路径、v4 listener） |
| 动作分布 | 20 judge + 1 deny | **全部 deny**（21 条 deny + 1 条 ask） |

判据不是记忆，是**代码**：`db/db.go` 的四个 seed 函数（`seedDefaultInterceptRules`
V1/V2/V3/V4）里，每条规则的 `action` 都写死为 `deny`（v4 的 listener 是 `ask`）。
ARTEX-upstream 快照里也是全部 deny。

这个更正很重要，因为它把结论整个翻过来了：不是「规则误设成 judge 导致误报」，
而是**「规则层把每一类调用都拍板了，模型从来没机会看这些命令」**。

### 历史教训（提交 39d5516，2026-10-20）

历史上曾手工把测试机的 21 条规则**全改成 judge** 跑真实任务，暴露三个问题：

1. **裁决 100% 失败**——裁决请求硬编码 `thinking.type=disabled`，MiniMax-M3.1
   这类强制 adaptive thinking 的模型直接 400。**已修**（改为不发 thinking 字段）。
2. **失败策略 allow** —— 模型挂了静默放行 = 关卡敞开。**已修**（改为 ask）。
3. **规则误报把合法探测拦死**——11 次真实调用被直接 deny。**已修**（收窄两条
   规则的 pattern，并留下回归基线 `db/intercept_rule_fp_test.go`）。

所以「全部改成 judge」这条路**已经被验证过一次并留下了坑**。本次整改不是
重蹈覆辙，而是在**已修好的基础上**做有依据的分层。

### 仍然存在的问题

| # | 严重度 | 问题 | 后果 |
|---|---|---|---|
| **P0** | 高 | 规则上的 `timeout_enabled` / `timeout_seconds` / `timeout_action` **是死字段**——只在 CRUD 存取，裁决路径（`intercept.judge()`）完全没读 | 界面上每条规则显示「超时 60s / 超时后 deny」，实际是「全局 180s / ask」。**用户看到的和实际做的不一致**，比没这字段更糟 |
| **P1** | 高 | 全部规则一律 deny，「明令禁止」与「交 Agent 研判」在规则层没有分开 | 「删自己建的测试表」这种合法操作被直接拦死，任务中断；而模型裁决能力（提示词写得很完整）**从未被内置规则用上** |
| **P2** | 中 | 「数据外泄管道」规则默认**停用**，且 pattern 会误伤正常回连（`curl 目标 \| nc 自己的回连器`） | 该防的没防（把凭证 POST 出去），不该防的想防 |
| **P3** | 低 | `rm -rf <任意路径>` 只能靠 fallback judge 兜 | 依赖 LLM 可用，模型抖动时会漏 |

## 二、整改方案

### A. 划清「明令禁止」与「交给 Agent 研判」

判据用**两根轴**，与裁决提示词（`intercept/prompt.go` 的 D1–D6 / A1–A6）一致：

```
不可逆性 × 作用对象
```

- **不可逆 且 作用对象与上下文无关** → **明令禁止**（`deny`，不调模型）
- **不可逆 但 作用对象取决于上下文** → **交给 Agent 研判**（`judge`）
- **与目标资产无关、只改平台自身** → **人工确认**（`ask`）

「明令禁止」的口径是**保守**的：要求**任何语境**下都不可逆且无合法渗透用途。
仅仅「通常很危险」不构成硬禁——硬禁砍掉的是「越权删除」这类漏洞的验证能力。

#### A1. 明令禁止（10 条，`deny`）

| 规则 | 理由 |
|---|---|
| 磁盘格式化 mkfs | 格式化任何块设备都不可逆；测试不需要 |
| 覆写磁盘设备 dd of=/dev/X | 同上 |
| 磁盘擦除 shred / wipe /dev/X | 同上 |
| Fork 炸弹 | 必然拖垮宿主；无合法用途 |
| 杀死全部进程 kill -9 -1 / killall -9 | 不可逆地打断所有服务；测试不需要 |
| 清空防火墙规则 iptables -F / nft flush | 抹掉宿主安全策略；与目标资产无关 |
| 关机 / 重启（系统级） | 中断宿主与所有任务（裁决 D5） |
| Redis FLUSHALL / FLUSHDB | 清空整个缓存/持久化集 |
| SQL DROP DATABASE / SCHEMA | 整个库/结构不可逆；验证注入用 DROP TABLE 足够 |
| 清空系统关键目录 | 宿主关键目录树被清空，必然破坏宿主 |

#### A2. 交给 Agent 研判（12 条，`judge`）

递归强制删除 rm -rf、删除系统关键目录、SQL DROP TABLE/INDEX/VIEW、SQL TRUNCATE、
MongoDB drop、curl/wget DELETE、Python HTTP 客户端 DELETE、脚本中声明 DELETE、
批量清空接口路径、删除类接口路径、破坏性系统命令（兜底）、数据外泄管道。

**理由**：被删/被改的对象**取决于上下文**——可能是本次测试建的测试表
（合法清理），也可能是生产数据（破坏，对应 D4）。裁决策略的原文例子就是
`rm -rf /var/www/html`、`DELETE /api/orders/8821`、`DROP TABLE users_bak_0921`
——规则层看不到这个区别，模型看得到完整参数。

#### A3. 人工确认（1 条，`ask`）

listener 启停回连接收器：开监听端口是**平台能力边界**与资源占用的变更，
不是「目标资产会不会被破坏」。让模型裁决「要不要开端口」是错位的。

### B. 让规则自己的 timeout 真正生效（修 P0）

1. `judge()` 增加规则级 timeout 覆盖参数。
2. 规则级 `timeout_enabled=false` → 用全局 `llm_judge_timeout_seconds` +
   全局 `llm_judge_fail_action`。
3. 规则级 `timeout_enabled=true` → 用规则自己的 `timeout_seconds` +
   `timeout_action`（**规则作者的显式声明**，优先于全局）。
4. 研判类规则统一声明 `timeout_enabled=true, 90s, allow`——
   **默认放行而不是拒绝**：研判类命中的操作**本身可能是合法的**，模型超时
   只是「没答上来」，判成拒绝等于模型一抖动就误伤合法操作。真正危险的类别
   已经单独划成硬禁，那边才是「超时即拒绝」。

### C. `rm -rf <任意路径>` 的覆盖缺口（修 P3）

**不新增通用规则**——那会误伤大量正常清理（`rm -f /tmp/out.$$`、
`rm -rf ./workdir`）。该类操作由 **fallback judge** 覆盖（裁决策略 D4 的原文
例子就是 `rm -rf /var/www/html`）。若后续观察到漏网再单独设计。

### D. 重新设计「数据外泄管道」pattern（修 P2）

旧 pattern（会误伤正常回连，导致该规则长期停用）：

```
(?i)(curl|wget|nc|ncat)\b[^|]*\b(\|\s*(curl|wget|nc))
```

新 pattern（只拦「@文件上传」，管道回连不再匹配）：

```
(?i)\b(curl|wget)\b[^|;&\n]{0,200}(?:-d|--data(?:-binary|-raw)?|-F|--form|--upload-file|--post-file)(?:\s*=\s*|\s+)?[^|;&\n]{0,100}?[\s"'=]@(?:"[^"\n]{0,80}"|'[^'\n]{0,80}'|[^\s;|&"']{1,80})
```

判别点是 **`@` 前面的那个字符**：文件引用形态里 `@` 前面必然是空白、引号或
等号（`@file`、`"@file"`、`name=@file`），而 `@` 出现在别处时前面是普通字符
（邮箱 `a@b.com`）。用 `[\s"'=]@` 锚定同时覆盖了五种形态，又不会把邮箱误判。

规则从 `enabled=false` 改为 `enabled=true`。

### E. 顺带修两个小问题

- `server/intercept.go` 的 `validateInterceptRuleReq` 校验 `timeout_action`
  ∈ allow|deny（该字段现在真的生效，写进任意值会让「超时后放行还是拒绝」
  变成未定义行为）。
- 界面规则列表显示「本规则的超时策略」（修好之前它显示的值与实际生效的不符）。

### F. 顺带修三个 nil-db 崩溃点

`intercept.loadLocked` / `Log` / `HandleAsk` 在 `i.db == nil` 时解引用 panic。
这三个都在**工具调用的同步路径**上——一崩就是整个 agent 进程死掉。

timeout 的规则**一律不动**。

## 四、验证

1. **分类测试**（`db/intercept_builtin_rules_test.go`）：明令禁止 10 条各自能抓
   到对应命令；研判类 12 条的 action 必须是 judge；每条规则都有分类理由；
   名字唯一；正则能编译。
2. **外泄 pattern 测试**：5 种上传形态命中，8 种正常回连/普通 POST 不命中，
   邮箱 `a@b.com` 不误伤。
3. **迁移测试**（`db/intercept_builtin_migration_test.go`）：占位符编号连续、
   占位符数与参数数一致、判据含「用户没动过」指纹、每条规则都有迁移语句。
4. **规则级 timeout 测试**（`intercept/rule_timeout_test.go`）：规则级超时
   覆盖全局、enabled=false 回落全局、失败动作按规则声明、不泄漏到全局。
5. **端到端分流测试**（`guard/intercept_e2e_test.go`）：明令禁止 → 拒绝且
   **不调模型**；研判 → **调模型**且以裁决为准；规则级 timeout 真的传到裁决器。
6. **校验测试**（`server/intercept_rule_validation_test.go`）：`timeout_action`
   只接受 allow/deny；启用超时时 seconds 必须为正。
7. **回归**：`go build ./...` + `go vet ./...` + `go test ./...`。
   失败集合与整改前基线**完全一致**（23 个，全部是「缺数据库配置」与
   「Windows 路径分隔符」两个既有的环境问题），零新增失败。
8. **前端**：`npx tsc --noEmit` + `NEXT_EXPORT=1 npx next build`。

## 五、不做的事

- ❌ 不改拦截架构（规则 → judge → allow/ask/deny 三分支保持）
- ❌ 不改 judge 提示词（D1–D6 / A1–A6 策略本身写得好）
- ❌ 不删任何规则（只改 action / pattern）
- ❌ 不给「rm -rf <任意路径>」加通用规则（误伤正常清理；由 fallback judge 覆盖）
- ❌ 不动用户自建的规则
- ❌ 不把全部规则改成 judge（那是一次已被验证会出事的路）
